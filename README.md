# АЛЛЮР — цифровой двойник автомобильного завода

Адаптация DigitalTwin.ai под кейс №2 Qostanai Industry Hackathon. Интерактивный MVP: условная линия из 30 станций, 5 производственных участков, мониторинг KPI, инциденты, прогнозы и управленческая аналитика. Данные и планировка демонстрационные, не фактические показатели АЛЛЮР.

## Что нужно для запуска

- Python **3.11** с модулями `pip` и `venv` — версия, на которой проверен проект.
- Распакованная папка адаптированного проекта `DigitalTwin-ai` с `app.py` и `requirements.txt`.
- Интернет для первой установки зависимостей и браузер для интерфейса.

После установки приложение работает локально без API-ключей. Все команды ниже выполняются из папки проекта. Примеры `cd DigitalTwin-ai` предполагают, что терминал открыт в родительской папке; при необходимости укажите полный путь в кавычках.

### Windows (PowerShell)

Установите Python 3.11, включив «Add python.exe to PATH». Откройте новое окно PowerShell и проверьте версию:

```powershell
python --version
```

**Первый и повторные запуски:**

```powershell
cd DigitalTwin-ai
powershell -ExecutionPolicy Bypass -File .\run.ps1
```

Скрипт создаёт `.venv`, если окружения ещё нет, устанавливает недостающие библиотеки и запускает приложение. Параметр `ExecutionPolicy` применяется только к этому запуску PowerShell.

**Ручная установка и запуск**, если хотите выполнить шаги самостоятельно:

```powershell
cd DigitalTwin-ai
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app.py --server.address 127.0.0.1 --server.port 8501 --server.headless true --browser.gatherUsageStats false
```

### Linux (Terminal)

Установите Python 3.11 с поддержкой `pip` и `venv` средствами вашего дистрибутива. Проверьте, что команда доступна:

```bash
python3.11 --version
```

**Первая установка и запуск:**

```bash
cd DigitalTwin-ai
python3.11 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m streamlit run app.py --server.address 127.0.0.1 --server.port 8501 --server.headless true --browser.gatherUsageStats false
```

Если создание окружения сообщает об отсутствии `venv` или `ensurepip`, установите пакет поддержки виртуальных окружений для выбранного Python в вашем дистрибутиве, затем повторите создание `.venv`.

**Повторный запуск** из папки проекта:

```bash
.venv/bin/python -m streamlit run app.py --server.address 127.0.0.1 --server.port 8501 --server.headless true --browser.gatherUsageStats false
```

### Открытие интерфейса и остановка

После появления адреса сервера откройте [http://127.0.0.1:8501](http://127.0.0.1:8501) в браузере. При первом открытии дождитесь обучения демонстрационных моделей. Терминал должен оставаться открытым. Для остановки сервера нажмите **Ctrl+C**.

Если порт 8501 уже занят этим приложением, откройте существующий интерфейс. Для запуска отдельного экземпляра используйте ручную команду, заменив `--server.port 8501` на `--server.port 8502`, и откройте `http://127.0.0.1:8502`.

Локальный запуск и тесты проверены на Windows. Инструкции для Linux и macOS используют стандартные пути Python-окружений; отдельная проверка на этих ОС не выполнялась.

## Проверки

После установки окружения выполните из папки проекта:

**Windows (PowerShell):**

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
```

**Linux и macOS:**

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Тесты проверяют формулы KPI, остановку и восстановление, распространение узкого места, риск брака, отсутствие датчиков, контракт CSV, неизменность состояния при ошибке импорта, жизненный цикл инцидентов и Streamlit UI. Это проверки проекта по требованиям PDF; скрытые тесты организатора не предоставлены.

## Источники данных и определения

Симуляция обновляет снимок по кнопке или каждые 3 секунды. Снимок представляет скользящее окно 60 минут; шаг симуляции не равен минуте работы завода. В демо выпуск последующих станций ограничен минимальной пропускной способностью предыдущих. Демосчётчики качества рассчитываются из отклонений процесса отдельно от ML-рисков, потери качества передаются к выходному контролю. Это агрегатная модель последовательной линии без физических буферов и транспортных задержек.

CSV — ручная загрузка одного полного синхронного снимка. После импорта симуляция выключена; следующий CSV создаёт новую запись истории. Для возврата в демо нажмите «Сброс». Шаблон `data/allur_snapshot.csv` также скачивается из интерфейса. Старый upstream `data/sample_factory.csv` не содержит счётчиков ОТК и окна наблюдения и не подходит новому контракту без этих дополнительных данных.

Обязательные поля: `station_id, station_type, sensor_level, cycle_time, temperature, vibration, torque, queue_length, throughput, downtime_min, window_min, total_count, good_count`. Станции S01–S30, типы Body/Paint/Trim/Chassis/Final из config.yaml. Sensor level: rich/partial/manual. Пустые значения разрешены только для temperature/vibration/torque; при manual все три должны быть пустыми. Время цикла в секундах, температура °C, вибрация мм/с, момент Н·м, throughput авто/ч, downtime_min и window_min в минутах. total_count и good_count — целые счётчики за одно окно. Одинаковое окно на всех станциях. Дополнительные поля игнорируются; process_name берётся из конфигурации.

- Производительность завода: `total_count последней станции × 60 / window_min`, не сумма выпуска всех станций.
- Загрузка станции: `total_count × cycle_time / ((window_min − downtime_min) × 60)`, ограничение 0–100%; при полном простое 0. Верхнее ограничение защищает отображение при несовместимых счётчиках, но для пилота такие данные нужно отдельно сверять.
- Простой оборудования: сумма `downtime_min`, в машино-минутах, не суммарный простой линии.
- FPY: `good_count / total_count` выходного ОТК. При нулевом выпуске — «Нет выпуска».
- OEE: доступность × производительность × FPY выходной станции; номинальная мощность 72 авто/ч — демопредположение.
- Прогноз смены: текущая производительность ОТК × 8 ч, сравнение с условным планом 500 авто.

## Ограничения и пилот

ML обучается на синтетических метках; AUC/F1 измеряют воспроизведение синтетической закономерности, не точность на заводе. Прогноз риска — сигнал для проверки возможных простоев; отдельная модель времени до отказа не обучена. «Полнота данных» — эвристика доступности датчиков, не точность модели. Тренд — линейная экстраполяция последних 8 снимков, ETA в шагах, не в минутах. Потеря датчиков уменьшает полноту данных, но не подавляет риск.

История ограничена 240 снимками. Журнал и состояние живут в сессии браузера и теряются после сброса/перезапуска; для сохранения скачайте CSV. Нет PLC/MES-интеграции, авторизации, постоянной БД или управления оборудованием. Склад и отгрузка на схеме — границы потока без собственных измерений.

Для пилота нужны реальная схема, согласованные окна/номиналы KPI, read-only адаптеры MES/PLC/ОТК, хранилище, разграничение доступа, обучение и проверка по историческим отказам, аудит решений оператора.
